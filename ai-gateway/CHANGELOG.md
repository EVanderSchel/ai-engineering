# Changelog

All notable changes to this project are documented here, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) conventions. This project uses [Semantic Versioning](https://semver.org/) (`MAJOR.MINOR.PATCH`). Releases are tagged `ai-gateway-vX.Y.Z`.

## [Unreleased]

### Added

- Step 0: project scaffolding (uv, ruff, pytest), CI with change detection (lint, tests, dependency audit), weekly Dependabot updates.
- Step 1: design doc (`docs/design.md`): responsibilities, architecture, the OpenAI-compatible API, routing and resilience rules, budgets and rate limits in PostgreSQL, guardrails, self-hosted inference, observability, the memory budget for the local cluster, and 15 numbered decisions.
- Step 2: the minimal gateway. `POST /v1/chat/completions` (OpenAI-compatible, streamed or not), `GET /v1/models`, health checks; API keys checked by SHA-256 hash; routes from `config/routes.yaml` (`smart`: Claude Sonnet 5.5 with server-side refusal fallback, `fast`: Claude Haiku 4.5, `stub`: offline echo); the Claude API adapter on the official SDK (2.x, API version 2026-10-21) and a stub provider; errors in OpenAI's shape with honest statuses; tests including the official OpenAI Python client. Design decision 16: `temperature` and `top_p` only on routes whose every candidate accepts them.
- Step 3, stage 1: retries, fallback and circuit breakers (`src/router.py`). Temporary errors retried once with jittered backoff, then the next candidate; timeouts per candidate (`first_token`, `attempt`); streams switch only before their first byte; a breaker per provider model; response headers `x-gateway-provider`, `x-gateway-attempts`, `x-gateway-fallback`; 503 `all_candidates_failed` / `all_candidates_paused` and 504 when nothing answers. The stub provider became a fault injector.
- Step 3, stage 2: `src/measure_resilience.py` and `results/resilience.{json,md}`: seven injected-outage scenarios, each with the gateway, one candidate and direct calls, plus a recovery timeline. With a hard outage or a slow primary the gateway served 100% (direct: 0%), with a 30% flaky primary 100% (direct: 64.5%); mid-stream drops can't be rescued; no request passed its deadline.
- Step 3, stage 3: Amazon Bedrock provider (`src/bedrock_provider.py`, Converse and ConverseStream through boto3 in a worker thread, no boto3 retries). `smart` falls back to Sonnet 4.6 on Bedrock; `fast` tries Haiku 4.5 on Bedrock first. Claude API-only route options are refused on other providers.
- Step 3, stage 4: an adapter for OpenAI-compatible servers (`src/openai_compatible_provider.py`), registered as the `local` provider for llama-server (step 6). `httpx2` is now a declared dependency.
- Step 4, stage 1: PostgreSQL. A local container (`docker-compose.yml`, PostgreSQL 17, port 5433), numbered SQL migrations applied by `src/migrate.py` (one transaction per file, an advisory lock, checksums), migration 001 (`teams`, `api_keys`), database tests on a fresh database each, and a PostgreSQL service container in CI.
- Step 4, stage 2: API keys in PostgreSQL. Admin commands (`src/admin.py`: teams, issue/list/revoke keys), every change in the audit log (migration 002), a key store checked per request (revocation is immediate), teams limited to routes (403 `route_not_allowed`), 503 `auth_unavailable` when the database can't be reached, a connection pool (`src/db.py`), and `src/serve.py` to run locally on Windows.
- Step 4, stage 3: rate limits, budgets and the usage ledger (`src/accounting.py`, migration 003). Token buckets per key (requests and tokens per minute), a budget hold per request settled to the real cost, a dated price list (startup refuses unpriced route models), one usage row per admitted request; admin `team budget` and `team spend`. 50 concurrent requests against a $0.50 budget: 13 served, 37 refused, never overspent.
- Step 4, stage 4: `/readyz` checks the database (503 when unreachable; `/healthz` unchanged), and startup refuses a database whose migrations don't match the code's. Design doc section 5 updated to the tables as built.
- Step 5, stage 1: personal-data detection and redaction (`src/pii.py`: SSN, card, bank, email, phone; kinds and positions only), 35 labelled made-up cases, and `src/measure_guardrails.py` (recall 92%, precision 96%, about 0.2 ms per KB).
- Step 5, stage 2: prompt-injection screening (`src/injection.py`): seven pattern rules and a model judge (Claude Haiku 5.5, low effort, structured output), on 60 labelled messages split dev/held-out (`data/guardrails/injection_cases.json`, `src/judge_cases.py`). Held-out: patterns 9 of 15, judge 15 of 15, no false alarms for either; data-shaped attacks 1 of 7 vs 7 of 7. $0.0076 for both judge runs.
- Step 5, stage 3: guardrail policies (`src/guardrails.py`, migration 004). Per route (`routes.yaml`) and per team (`admin.py team guardrails`, can only tighten): personal data off/flag/redact/block in and out, injection off/flag/block with an opt-in judge that decides when on. Checks run after admission (the judge is held for and charged to the team), redaction before the judge; streams that may be redacted or withheld are buffered; blocked requests get a `blocked` ledger row; every finding is audited without text. Design decisions 17-18.
- Step 5, stage 4: `src/measure_guardrail_latency.py` and `results/guardrail-latency.md`. The free checks add about 1 ms per request; the judge about 1.3 s (p95 2.9 s) and $0.00013; a route that checks answers before sending them shows the first word at 1.5 s instead of 343 ms on a paced stub.
- Step 6, stage 1: a self-hosted model. Qwen2.5-0.5B-Instruct (Q4_K_M) on llama-server (`docker-compose.yml` service `llm`, profile `local`, image pinned by digest, 4 parallel slots, published on 127.0.0.1:8081), a `local` route with no fallback, $0 price rows per quantization (migration 005). The adapter's default address is now `127.0.0.1:8081`, and a prompt over llama-server's context returns 413 `request_too_large` instead of 400.
- Step 6, stage 2: `src/measure_quantization.py` and `results/quantization.{json,md}`: Q4_K_M, Q8_0 and F16 compared on this PC's CPU (load, peak memory, speed at 1-16 at once, fidelity to F16, ARC-Easy and NTEE accuracy, cost per 1,000 requests at a cloud CPU's hourly price). Q8_0 is fastest under load (61 vs 46 tokens/s for Q4_K_M) and matches F16's ARC-Easy accuracy (65.2%; Q4_K_M 63.0%); throughput stops growing past the server's 4 slots; the plain model scores below the majority class on NTEE at every precision. New data: 400 ARC-Easy test questions (CC BY-SA 4.0) and 400 NTEE dev rows.
- Step 6, stage 2 decision: the `local` route and the `llm` service default to Q8_0 instead of Q4_K_M; the cluster memory budget is updated to about 3.25 GB.
- Step 6, stage 3: the NTEE classifier from ntee-classification on ONNX Runtime. A Colab notebook (generated by `notebooks/make_export_notebook.py`) merges the LoRA adapter and exports fp32 and int8; `src/measure_classifier.py` measures each on the 1,813 dev missions (fp32 58.7%, the same as PyTorch; standard dynamic int8 19.0%); `src/quantize_classifier.py` traces the int8 damage to outlier activations at the MLP down projections, plus AVX2 overflow (57.8% with those 24 matrices in fp32). New `classifier` dependency group: onnxruntime, tokenizers, onnx.
- Step 6, stage 3 decision: the classifier is 8-bit weight-only (`MatMulNBits`, made by `src/quantize_classifier.py`): 58.8% on the dev split (fp32 58.7%), 1.46 GB peak memory (fp32 2.4 GB), about 1 s per mission on this CPU (fp32 149 ms). Block-quantized activations (`accuracy_level=4`) and 4-bit versions were measured too. `onnx-ir` added to the `classifier` group; the cluster memory budget is now about 3.95 of 3.8 GB, to be resolved in step 8.
- Step 6, stage 4: the GPU comparison. A Colab notebook (generated by `notebooks/make_vllm_notebook.py`) serves Qwen2.5-0.5B-Instruct (fp16) on vLLM on a T4 and runs stage 2's measurement against it. `src/measure_quantization.py` adds the run to `results/quantization.md` at its own hourly price. Results: 181 tokens/s for one request (CPU Q8_0: 31), 3,700 tokens/s in total at 64 at once (CPU: 61), a 91 ms first token at 16 at once (CPU: 27 s), $0.0034 per 1,000 128-token answers (CPU: $0.21), and ARC-Easy accuracy equal within noise. vLLM is started with `--generation-config vllm`: by default it applied the model's repetition penalty, which skewed the first run's answers. Step 6 complete.
- Step 7, stage 1: structured logs (`src/logs.py`). One JSON line on stdout per request, written when its response has been sent, with the request id (also the `x-request-id` header and the usage row's), team, route, each provider attempt, fallback, outcome, model, tokens, cost, first-token time and guardrail kinds; never content. Other lines logged during a request carry its id. Health checks aren't logged, uvicorn's access log is off, and `GATEWAY_LOG_LEVEL` sets the level.
- Step 7, stage 2: Prometheus metrics (`src/metrics.py`, `prometheus-client`) on their own port (`GATEWAY_METRICS_PORT`; `serve.py` uses 9464). They cover requests by route, status and outcome; latency and first-token histograms; provider attempts; fallbacks; tokens and cost by team; guardrail findings; requests in flight; breaker states, read at scrape time; and team budgets, re-read from PostgreSQL every 30 s. Each request is counted from its log line's fields, and labels only take values the gateway controls.
- Step 7, stage 3: OpenTelemetry traces (`src/tracing.py`), exported over OTLP when `OTEL_EXPORTER_OTLP_ENDPOINT` is set (Jaeger in `docker-compose.yml`, profile `observability`). FastAPI's own request span carries the gateway's attributes. Inside it are spans for auth, admission, the input and output guardrails, each provider call (`chat <model>`, with `gen_ai.*` attributes, retries and error kinds) and the ledger write; a breaker-skipped candidate is an event. Log lines carry `trace_id`, and a caller's `traceparent` is continued. No content in spans.
- Step 7, stage 4: a dashboard and alerts. Prometheus and Grafana run in `docker-compose.yml` (profile `observability`, images pinned by digest), configured from `observability/`. The Grafana dashboard is generated by `make_dashboard.py` and checked by `tests/test_dashboard.py`: it's current, and its charts and alerts only name exported metrics. Six alert rules: error rate, latency, first token, breaker open, cost spike, budget nearly spent. They're unit-tested with promtool (`alerts_test.yml`), which CI also runs.
- Step 7, stage 5: proof.
  - `src/measure_alerts.py` ran the gateway with injected faults against the local Prometheus. 5 of the 6 alerts fired once their `for:` time ran out, and no other alert did. 4 resolved 0.4 to 3.6 minutes after the faults stopped; the budget alert stays, because the money is spent. `GatewayCostSpike` needs a day of history, so its proof is the promtool tests.
  - `src/measure_observability.py` measured the cost per request: metrics are in the baseline, the JSON log line adds 0.16 ms and traces about 1 ms (9 spans), against 30-45 ms for PostgreSQL. Step 7 complete.
- Step 8, decision: the NTEE classifier stays out of the cluster in this step. It doesn't fit Docker's 3.77 GB alongside everything else, and it isn't a service yet. The cluster budget without it is about 2.55 GB.
- Step 8, stage 1: a container image (`Dockerfile`, `.dockerignore`). It's built in two stages with uv from `uv.lock`, on `python:3.14.10-slim`, with both base images pinned by digest. It has production packages only, runs as non-root user 10001, and shuts down gracefully on SIGTERM. It's 345 MB and uses 123 MiB running. A new CI job, `ai-gateway-image`, builds it, starts it and checks it; Dependabot now updates its base images.
- Step 8, stage 2: a kind cluster (`k8s/kind.yaml`: one node, Kubernetes 1.37, the API on 127.0.0.1:8088) and a Helm chart (`chart/ai-gateway`).
- Step 8, stage 3: llama-server in the cluster (`templates/llm.yaml`: one replica, Recreate, non-root, read-only root filesystem, ClusterIP only), with the Q8_0 model read from the node's `/models` mount. The gateway reaches it via `GATEWAY_LOCAL_URL`; `llm.enabled=false` leaves it out. Live: streamed first text in 0.13 s, 4 at once in 2.7 s, a 503 in 0.3 s with the server stopped, 19 s to serve again; llama-server 466 MiB, the whole node 1.67 GiB of Docker's 2.84 GiB.
- Step 8, stage 4: Prometheus, Jaeger and Grafana in the cluster (`templates/observability.yaml`), with the repo's alert rules and dashboard passed in by `--set-file`. Prometheus discovers pods by annotation, using a Role limited to reading pods in its namespace; traces carry `k8s.pod.name`; the UIs are reached by port-forward only. Grafana no longer downloads plugins at start (chart and compose). The first try ran the node out of memory: the memory-mapped model was evicted and a 37-token prompt timed out after 60 s. Fixed by raising WSL's memory cap from 3 to 4 GB, and Grafana's limit to 640 MiB. Live: all targets found, requests counted per pod, 60 traces split 31/29 by pod, a replaced pod scraped after 17 s with no config change; the node 2.43 GiB of 3.83 GiB.
- Step 8, stage 5: autoscaling. metrics-server v0.9.1 (`k8s/metrics-server.yaml`, upstream's manifest with `--kubelet-insecure-tls` for kind), a HorizontalPodAutoscaler for the gateway (2-4 pods, 50% CPU, 2-minute scale-down window), a CPU request of 200m from a measurement, and a k6 load test (`load/chat.js`). Readiness now answers from a background database check on its own connection (`db.Health`, design decision 19), and both probes allow 5 s per try: under load, readiness through the request pool took busy pods out of service during a scale-up (5.5% failed, ready pods down to 1 of 4). After the change, the same test had 0% failed and p95 865 ms (was 8.9 s). Also found: one team at 40 requests a second is limited by its own rate-bucket and budget rows in PostgreSQL (p95 2-4 s, vs 66 ms for the same load over 20 teams); not fixed yet.
- Step 8, stage 6: rolling updates without dropped requests. The gateway's pods pause 5 s before shutting down (`preStop` with Kubernetes's sleep action, `gateway.preStopSeconds`), so they leave the Service before uvicorn stops accepting connections. Under a steady 12 requests a second with two rolling updates: 16 of 2,964 failed with `EOF` before (each at a pod's stop), 0 of 2,964 after; p95 176 → 45 ms. `load/chat.js` logs non-200 answers.
- Step 8, stage 7: memory measured against the step 1 budget (design doc section 9 now has the measurements): the whole node 2.19 GiB with 2 gateway pods and 2.46 GiB with 4 at idle, about 2.8 GiB with the model resident, of Docker's 3.83 GiB. No separate OpenTelemetry Collector: Jaeger v2 receives OTLP itself. Step 8 complete.
- Step 9, decisions: the eval canary runs in CI with real models on PRs that change routes or prompts (stub everywhere else), on the NTEE dev missions and ARC-Easy questions (exact answers, scored in code); apps name registered prompts in the `gateway` object.
- Step 9, stage 1: a prompt registry (`src/prompts.py`, `prompts/<name>/<version>.txt` + `manifest.json` with SHA-256 fingerprints; `register`, `activate`, `list` commands). Requests use `{"gateway": {"prompt": "name[@version]", "variables": {...}}}`; the rendered prompt is the whole system prompt (a request may not also send one). The version and fingerprint are in the `x-gateway-prompt` headers, the log line, the trace and the usage ledger (migration 006). `GET /v1/prompts` lists them. Variable values are screened by the guardrails like a user message and never logged. An edited published version stops startup. First prompt: `ntee-classify@v1`, Project 4's guided prompt with a plain-text answer format.
- Step 9, stage 2: the eval canary (`src/canary.py`, checks in `config/canary.yaml`). Each check sends a fixed set of questions with exact answers (60 NTEE dev missions for `fast` and `smart` with `ntee-classify`, 100 ARC-Easy questions for `local` at temperature 0) through the gateway in memory, parses and scores each answer, and compares with the check's baseline item by item: it fails if accuracy falls more than the margin (0.05, a placeholder until stage 3) below the baseline's, reports answers that broke and that were fixed, and calls a run with more than 5% failed requests incomplete rather than worse. A check's subject (the route's candidates and the prompt's version and fingerprint) lets `--changed` skip unchanged checks. `--stub` runs every check on a scripted model for free, against baselines in `results/canary/stub/`. No real model was run yet.
- Step 9, stage 3: live baselines and the CI gate. Each check ran three times unchanged, with the Claude API only (`fast` falls back to Haiku 4.5 there, as in CI): `ntee-fast` 50.0-53.3% (top-1 results changed on 2 of 60 between runs), `ntee-smart` 68.3% each time, `arc-local` 69.0% with identical answers. The margin stays 0.05, now measured. The first run found that a 20-token cap left 3 Sonnet 5.5 answers empty (thinking used it up); the cap is 256 and each item records its finish reason. New CI job `ai-gateway-canary`: the scripted run on every PR, then the NTEE checks on real models only when their subject differs from main's baseline (`--baseline-ref HEAD^1`), compared with main's baselines (a check with none there is skipped rather than paid for); runs uploaded as an artifact. Needs the repository secret `AI_GATEWAY_CANARY_ANTHROPIC_API_KEY`. About $0.27 per run of both NTEE checks; stage 3 cost $1.09.
  - The chart: the gateway as a Deployment of 2 with a rolling update, a NodePort Service and a disruption budget; PostgreSQL as a StatefulSet with a volume; routes from a ConfigMap; migrations in an init container.
  - Startup, liveness and readiness probes; requests and limits; a locked-down security context. The Secret comes from `k8s/make_secret.py`, outside the chart. CI lints and renders the chart.
  - Measured live: the node uses 1.4 GiB. Connections, not requests, are balanced. Deleting a pod under traffic lost 1 request in 111 (for stage 6). A database outage marks the pods not ready without restarting them.
